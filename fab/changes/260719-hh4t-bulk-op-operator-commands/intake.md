# Intake: Bulk-Op Operator Commands

**Change**: 260719-hh4t-bulk-op-operator-commands
**Created**: 2026-07-19

## Origin

Backlog item `[hh4t]` (2026-07-19), promoted during a `/fab-discuss` session. The user's framing:

> Check the last backlog. The ability to run parallel updates in all shll tools, is something I would need again and again. how to go about this?

Key decisions from the conversation (beyond the backlog text):

1. **Monitoring is one-directional** — the user corrected an early framing: spawned per-repo agents do NOT register with fab-operator. "It's the fab-operator's job to monitor them, by definition. Not the other way round." The command writes no operator state.
2. **Convention: one tmux session per bulk task** — groups the per-repo windows; `fab pane map --all-sessions` already sweeps every session on the server, so grouped windows stay visible to the operator.
3. **Convention: repo-name suffix in window names** — each spawned window is self-identifying.
4. **Shape: generic primitive + two presets, `bulk-shll-` naming** — the user specified three commands by name: `bulk-shll-op` (generic primitive), `bulk-shll-fab-upgrade` (the fab upgrade-repo op), and `bulk-shll-release` ("releases patch version using `just release`").
5. **Gitignore approach settled empirically** — both candidate patterns from the backlog were tested in a scratch repo during intake (results in § What Changes).

## Why

1. **Pain point**: the fab-operator role repeatedly needs the same bulk operation across all 7 sahil87 toolkit repos (fab-kit, hop, idea, run-kit, shll, tu, wt) — e.g. "run `fab upgrade-repo` in a fresh worktree in every repo, then ship a PR if anything changed" (done ad hoc in change 260718; see also the std3 toolkit-naming rollout). Today each bulk op is improvised inline: a manual per-repo loop of `wt create --non-interactive`, spawn `fab agent --print --repo <repo>` in a tmux window, dispatch `/fab-new <description>` + `/fab-fff`, monitor via `fab pane map --all-sessions --json`, skip the PR when nothing changed.
2. **Consequence of not fixing**: every future toolkit-wide operation costs a fresh re-improvisation of the same loop — error-prone (missed repos, inconsistent PR-skip handling, unmonitorable windows) and slow.
3. **Why this approach**: codify the recipe as slash-command docs under shll's own `.claude/commands/`.
   - NOT `.claude/skills/` — that directory is entirely regenerated by fab-kit's embedded templates on every `fab sync`/`wt create`; anything placed there is silently overwritten. This also means the conventions cannot be added to the fab-operator skill file from this repo — they must live in the command docs. `.claude/commands/` is untouched by fab sync.
   - NOT a `shll` Go subcommand — Constitution VII (Minimal Surface Area) would rightly bounce a new top-level command for operator prompt tooling; no Go code is involved.

## What Changes

### 1. `.claude/commands/bulk-shll-op.md` — generic bulk-operation primitive (new)

A slash-command doc codifying the per-repo spawn loop as a repeatable primitive. It accepts/documents:

- **Target repos** — default: the 7-repo roster `fab-kit, hop, idea, run-kit, shll, tu, wt` (repo roots resolved via `hop <repo> where`, falling back to `~/code/sahil87/<repo>`); an explicit subset may be passed.
- **Per-repo task** — the recipe to run in each repo's fresh worktree, expressed as the single prompt/slash command delivered to the spawned agent (e.g. `/fab-new <description>` for a described op, or `/fab-fff <change>` for pre-created changes).
- **PR-skip rule** — the dispatched prompt MUST instruct each agent to skip `/git-pr` entirely when the recipe produced no diff (no empty PRs).

**Per-repo loop** (mirrors fab-operator §6's spawn sequence, minus enrollment):

1. Resolve the repo's main-worktree root.
2. `wt create --non-interactive` — fresh worktree per repo; capture worktree name `<wt>` and path.
3. Read that repo's session command: `fab agent --print --repo <repo-root>` (never the invoking repo's config).
4. Spawn: `tmux new-window -t <bulk-session> -n "<wt>-<repo>" -c <worktree-path> "<spawn_cmd> '<task>'"` — embed exactly **one** slash command per spawn (no `&&`-joined strings; a spawned agent reads one leading `/command` per prompt, per fab-operator §6).

**Conventions the doc encodes**:

- **One tmux session per bulk task**: create a dedicated session (default name `bulk-<task-slug>`) and open all per-repo windows in it. This groups the windows as a unit and keeps them visible to the operator via `fab pane map --all-sessions`.
- **Repo-name window suffix**: window name is `<wt>-<repo>` (e.g. `swift-fox-hop`), so every window is self-identifying at a glance.
- **No operator registration**: the command does NOT write the operator state file, does NOT add `branch_map` entries, and does NOT rename windows with the operator's `»`/`›` markers — those are the operator's own enrollment actions. Monitoring is the operator's job, one-directional; the session/window conventions exist purely to make the spawned agents discoverable and groupable by it.

### 2. `.claude/commands/bulk-shll-fab-upgrade.md` — fab-upgrade preset (new)

A thin zero-argument preset that invokes the bulk-op recipe with the op that recurs: for each roster repo, in the fresh worktree run `fab upgrade-repo`, then drive the change through the pipeline (`/fab-fff`) and ship a PR **only if anything changed**. This is the exact op improvised ad hoc in change 260718, made a one-command invocation.

### 3. `.claude/commands/bulk-shll-release.md` — patch-release preset (new)

Releases a patch version of every roster repo via `just release` (default bump: patch). **Verified during intake**: all 7 repos carry a `release` justfile recipe; shll's (the reference implementation) is tag-driven — `scripts/release.sh` computes the next semver from `git describe`, creates and pushes the tag, and CI takes over (cross-compile, GitHub Release, Homebrew tap bump). No tracked files change and the working tree must be clean.

This preset therefore does NOT use the spawn loop — no worktree, no spawned agent, no PR. It is a **direct sequential per-repo loop** run by the invoking agent:

1. Resolve the repo's main-worktree root; verify clean tree and up-to-date `main` (fetch + compare against `origin/main`).
2. **Skip repos with no new commits since the last tag** (`git describe` exact-match on HEAD) — the release-only-if-changed analogue of the PR-skip rule; report skips.
3. Run `just release` (patch) in the repo root.
4. Report per-repo outcome (new tag or skip/error) in a summary table.

**Confirmation gate**: pushing a tag publishes a release across up to 7 repos — the doc MUST have the agent present the repo → next-version list and get explicit confirmation before the first push. This is outward-facing and not reversible in the "delete quietly" sense (CI fires on the tag).

### 4. `.gitignore` narrowing

Current line 41 is a bare `/.claude`, which excludes the **directory itself** — git never descends into it, so any `!/.claude/commands/` negation beneath it is dead. Change:

```gitignore
# before
/.claude

# after
/.claude/*
!/.claude/commands/
```

**Empirically verified during intake** (scratch repo, `git check-ignore -v` + `git status --porcelain`, both backlog-suggested approaches tested):

- `/.claude/*` + `!/.claude/commands/` → `commands/bulk-op.md` is trackable; `.claude/skills/**` and `.claude/settings.local.json` remain ignored (matched by `/.claude/*`). No `!/.claude/commands/**` third line and no explicit `settings.local.json` re-ignore are needed — `/.claude/*` matches direct children only, and nothing else ignores paths under the negated `commands/` dir.
- Bare `/.claude` + `!/.claude/commands/` → confirmed broken: everything under `.claude/` stays ignored, including `commands/`.

### Out of scope

- **No multi-repo deployment** of the command docs: bulk ops are invoked from a session that has shll's commands loaded (typically the operator's context or a shll checkout) — never from inside each target repo's own session, so there is no deployment-parity requirement with fab-operator. Revisit only if a bulk op ever needs invocation from another repo's session.
- **No Go/CLI surface change**, no help-dump, README, or docs/site change (Toolkit Standards clause not triggered).
- **No fab-operator skill edits** — it is fab-kit-owned and regenerated; upstreaming the bulk conventions into fab-kit is a possible follow-up, not this change.
