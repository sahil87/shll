### Standard document: `shll agent-setup` section

#### R1: Rewrite § "Forward design" as a landed-design note
The § "Forward design: `shll agent-setup`" section of `docs/site/standards/skill.md` (currently lines 68–70) SHALL be rewritten in full as a **landed-design note** that describes the shipped `shll agent-setup` design in the standard's existing public, producer-facing register. It MUST cover: (a) **skills placement, not context aggregation** — `shll agent-setup` places one thin bootstrap Agent Skill (`shll-toolkit`) into the harnesses' global skills directories (`~/.agents/skills/` + `~/.claude/skills/`), with a roster-driven description (front-loading tool names as trigger words) and a body that teaches the runtime two-step; aggregating bundles into context and placing per-tool bundle skill files were both rejected (placed copies go stale between updates; per-tool skills multiply listing lines); (b) **the runtime two-step** — `shll skill` prints an installed-only glossary (one line per tool), `shll skill <tool>` streams that tool's core bundle on demand, byte-identical from the installed binary, so bundle content stays version-locked by construction; (c) **hook-wiring delegation** — `shll agent-setup` delegates run-kit's dashboard-hook wiring to `run-kit agent-setup`, which is hook-only today (its context-injection responsibility was removed as designed); (d) **why the ≤150-line + static-only rules still hold** — every `shll skill <tool>` call pulls the core bundle into a paying context and the glossary lists every installed tool, so a bloated bundle still taxes every conversation that pulls it.

- **GIVEN** the shipped `shll agent-setup` uses skills placement + the runtime two-step, not context aggregation
- **WHEN** a producer reads `docs/site/standards/skill.md`
- **THEN** the § describes the design via the commands (`shll agent-setup`, `shll skill`, `run-kit agent-setup`) as a landed design
- **AND** it contains no `(Planned, not yet built …)` framing and no "aggregate every installed tool's core `<tool> skill` output into the agent's context" claim

#### R2: Retitle the heading and retarget in-file anchors
The section heading SHALL be retitled to `## Landed design: \`shll agent-setup\`` (it is no longer a forward design), changing the anchor from `#forward-design-shll-agent-setup` to `#landed-design-shll-agent-setup`. The two in-file links that target the old anchor (at lines 45 and 51) SHALL be retargeted to the new anchor.

- **GIVEN** the heading is renamed and its anchor changes
- **WHEN** the two in-file `[Forward design](#forward-design-shll-agent-setup)` links are followed
- **THEN** each resolves to the renamed `#landed-design-shll-agent-setup` anchor within the same file
- **AND** no external file (docs/site or memory tree) references the old anchor, so no cross-file link update is required

#### R3: Reprice the budget rationale at its three cross-reference sites
The stale "N bundles concatenated into one payload" / "aggregate" pricing outside the rewritten section SHALL be repriced in the same pass at three sites: (a) **line 45** (§ Rules with teeth, "Bounded — ≤150 lines") — reprice from "bundles will later be *aggregated* across every installed tool … a bloated bundle taxes every conversation that pays for it" to: agents pull a bundle into a paying context at use time via `shll skill <tool>`, and the `shll skill` glossary aggregates roster one-liners — a bloated bundle taxes every conversation that pulls it; (b) **line 51** (§ Topic pages intro) — reprice from "The ≤150-line budget prices the toolkit-wide *aggregate*" to: the budget prices the use-time pull (each `shll skill <tool>` serves exactly one core bundle), so it deliberately does not scale with tool size; (c) **line 56** (§ Topic pages bullet) — correct the mechanism from "aggregation (`shll agent-setup`) reads **core bundles only**" to: the runtime two-step (`shll skill <tool>`) serves **core bundles only** — never topic pages, retaining the invariant "a tool's ambient context cost stays ≤150 lines no matter how many topics it ships". Sites (a) and (b) also retarget their link to the renamed anchor.

- **GIVEN** three sites outside the § still price a one-payload N-bundle concatenation
- **WHEN** the section is rewritten as a landed-design note
- **THEN** all three sites are repriced to use-time `shll skill <tool>` pulls (glossary aggregating one-liners only)
- **AND** lines 45 and 51 link to `#landed-design-shll-agent-setup`, and no other section of the standard references the forward design

#### R4: Preserve the public register (no internal change-IDs / PR numbers)

### Design Decisions

1. **Rewrite the whole § rather than patch the parenthetical**: *Why*: the section's framing ("Planned, not yet built"), mechanism ("aggregate … into the agent's context"), and closing rationale ("N bundles concatenated") are all stale together — a landed-design note is a coherent replacement. *Rejected*: surgically editing only the `(Planned …)` clause, which would leave the aggregation mechanism and N-payment rationale describing a rejected design.
2. **Retitle heading + retarget the two in-file anchors**: *Why*: "Forward design" is false once the note records a landed design; grep verified no external referencer targets `#forward-design-shll-agent-setup` (the three memory referencers point at `cli/standards-content.md`'s own section anchor, not this document's), so the rename is contained to this file. *Rejected*: keeping the stale "Forward design" title, which would misdescribe a shipped design.
3. **Public register preserved**: *Why*: the existing document cites no internal provenance; a producer-facing standard names commands, not change-IDs. *Rejected*: citing `agst`/PRs in the standard text (scope creep into provenance that belongs in memory).
