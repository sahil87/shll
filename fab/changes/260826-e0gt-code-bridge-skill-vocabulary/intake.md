# Intake: Code Bridge Skill Vocabulary

## Origin

One-shot `/fab-new` invocation (recorded in `.history.jsonl`; the intake file itself was not written by that run and was regenerated by `/fab-proceed` in promptless-defer mode — no user questions were asked):

> shll: extend run-kit Roster Description/ProactiveHint + shll-toolkit skill body with the rk code (code-bridge) capability so agents discover rk code exec via the placed skill

Key decisions were taken from the request text plus the run-kit repo's shipped Code Bridge artifacts (run-kit PR #745 `feat: Code Bridge — rk code exec + the rk-code-bridge code-server extension`, released in run-kit **v3.18.7**; `docs/site/skill/code.md` topic page; `docs/site/skill.md` core-bundle line; `docs/memory/run-kit/code-bridge.md`).

## Why

run-kit v3.18.7 shipped the **Code Bridge**: the `rk-code-bridge` code-server extension opens a same-user Unix socket per open folder, and the `rk code` CLI family is the shell side — `rk code exec <command> [json-arg…]` runs any VS Code palette command (including the GitHub Pull Requests extension's `pr.*` commands) inside the dashboard's `code` lens editor; `rk code hosts` lists live hosts; `rk code commands` grep-lists command ids; `rk skill code` serves the depth page.

This is an **agent-proactive** capability in exactly the sense shll's `ProactiveHint` was created for: a user says "refresh the PR list in the editor", "open the diff for this file", "focus the sidebar" — and never names run-kit. Today the only text an agent sees before any skill is invoked is the `shll-toolkit` SKILL.md description, and that description (single-sourced from `Roster` by `agentSkillDescription()` in `src/cmd/shll/agent_setup.go`) speaks only of visual display, port proxying, and notifications. An agent has no way to learn that palette commands are reachable from the shell unless it already runs `shll skill run-kit`, which it does not do unprompted for an editor-shaped request. Result: agents describe what the user should click instead of doing it.

If left as-is, the Code Bridge is discoverable only by agents that already know it exists — the placed skill silently under-advertises the toolkit. The fix belongs in shll (the manager) because the placed skill is a `shll setup agent` artifact built from the Roster (Constitution III — one source of truth), not in run-kit's own bundle, which is only read *after* activation.

Approach: extend the existing three Roster-driven surfaces rather than adding any new field, command, or file — the `ProactiveHint` mechanism, the `Description` one-liner, and the skill body's proactive-capabilities pointer line already exist for precisely this purpose.

## What Changes

### 1. `Roster` run-kit entry — `Description` (`src/cmd/shll/tools.go`)

Extend the `shll list` one-liner to name the editor-command capability. Current:

```
Run-kit — tmux session manager with a web UI; can display web pages/HTML to the user and push notifications (rk stays as an alias)
```

New (exact text):

```
Run-kit — tmux session manager with a web UI; can display web pages/HTML to the user, push notifications, and run VS Code palette commands in its code editor via `rk code exec` (rk stays as an alias)
```

### 2. `Roster` run-kit entry — `ProactiveHint` (`src/cmd/shll/tools.go`)

Add the code-bridge trigger vocabulary to sentence one (the reach-for-unprompted list), leaving sentence two (the skill-shadowing counter-instruction) byte-identical. The three existing load-bearing fragments pinned by `TestRosterProactiveHint` (`"to proxy a local http port"`, `"before opening any file or local port in a browser, read"`, `"publishing an artifact"`) MUST survive verbatim. New sentence one (exact text):

```
Also use proactively — without the user naming a tool — to show the user visual content (HTML, diagrams, reports, a local dev server) in a browser window, to proxy a local http port to the user's browser, to push a notification to their devices, or to act inside the user's code editor — run any VS Code palette command (refresh a PR list, open a diff, focus a view) from the shell with `rk code exec` (run-kit).
```

Sentence two is unchanged:

```
The user may be viewing this session remotely through run-kit's web dashboard, where `open`/`xdg-open` and localhost URLs never reach them and publishing to a hosted artifact page (e.g. claude.ai) forces them off the dashboard — before opening any file or local port in a browser, read `shll skill run-kit` for the proxied-iframe recipe; the same applies before publishing an artifact or hosted page to show the user something.
```

Invariants to preserve: the whole description stays a single line with no `: ` sequence (`TestAgentSetup_DescriptionSingleLine`); the hint is appended verbatim after the tool clauses and before the two-step pointer (`TestRosterProactiveHint`); exactly run-kit carries a `ProactiveHint` (sprawl guard — no new tool gets one). The new text contains ` — ` and backticks, both already present in the current value and both YAML-safe in an unquoted scalar.

### 3. `agentSkillContent` body pointer line (`src/cmd/shll/agent_setup.go`)

Current:

```
Run-kit also has agent-proactive capabilities — visual display in a browser window and push notifications; see `shll skill run-kit`.
```

New (exact text):

```
Run-kit also has agent-proactive capabilities — visual display in a browser window, push notifications, and running VS Code palette commands inside the user's code editor (`rk code exec`); see `shll skill run-kit` (and `shll skill run-kit code` for the editor bridge).
```

The body stays thin — one pointer line, no recipe; the recipe (gate on `rk code hosts`, resolve host by `--folder`/cwd, exit codes) lives in run-kit's own `rk skill code` topic page, fetched at request time (Constitution II/III — don't duplicate per-tool content).
