# Intake: run-kit Rename + Migration Guard

**Change**: 260709-9bak-run-kit-rename-migration-guard
**Created**: 2026-07-09

## Origin

Conversational — a `/fab-discuss` session that began as a diagnosis ("why doesn't `shll list` show rk installed on this MacBook?") and evolved into the migration design for the rk→run-kit rename. The user's raw asks, in sequence:

> Can you find out why when on this macbook if I do `shll list` I don't see rk installed? By the way, I am trying to rename run-kit from rk to just "run-kit". That change is partly done (check the run-kit repo at `hop run-kit where`)

> run-kit has now become the primary binary generated by run-kit repo, and also homebrew-tap has been updated to install that binary and keep rk as the alias. Whatever the update path is for users, if the user uses shll, it should update safely. "uninstall sahil87/tap/rk", "uninstall run-kit" (just to be safe) and only then "install sahil87/tap/run-kit" (Only for versions of run-kit / rk < v3): What do you recommend? The update should work cleanly via both paths: "shll update" and "shll update run-kit"

> formula_renames.json is done. Deletion of rk.rb done.

Key decision trail from the discussion:

1. The agent recommended the **Homebrew-native rename** (`formula_renames.json` + `rk.rb` deletion in the tap) over the user's proposed uninstall→install sequence for the routine path (no failure window; fixes non-shll users too). The user implemented the tap side immediately — it is **live** as a prerequisite.
2. The user's "only for versions < v3" gate was replaced by a **keg-presence gate**: `rk.rb` capped at 2.5.16, so an installed legacy `rk` keg ⟺ pre-v3 by construction. No version parsing.
3. The uninstall→install sequence was repurposed as the **repair path** — it lives in the sibling change `shll uninstall` (drafted alongside this one), not in the update flow.
4. Explicit user requirement: migration must work cleanly via **both** `shll update` (whole roster) and `shll update run-kit` (named target).

## Why

run-kit v3.0.0 completed the rename: the tap's `Formula/run-kit.rb` (class `RunKit`) installs the binary as `run-kit` with `rk` as a symlink alias (`bin.install "rk" => "run-kit"; bin.install_symlink bin/"run-kit" => "rk"`), `Formula/rk.rb` is deleted, and `formula_renames.json` maps `{"rk": "run-kit"}`. The tap's `all.rb` already depends on `sahil87/tap/run-kit`. v3's own updater targets `/Cellar/run-kit/` and `sahil87/tap/run-kit` (`app/backend/cmd/rk/upgrade.go`).

shll's hardcoded roster still points at the old identity (`src/cmd/shll/tools.go:94`): `Name: "rk"`, `Formula: "sahil87/tap/rk"`, `Update: {"rk", "update"}`. Without this change:

1. **`shll update` strands legacy machines.** `probeTool` (`update.go:445`) probes `brew list --formula --versions <Formula>`. Once the roster is renamed, a machine holding the legacy `rk` keg reports not-installed for `sahil87/tap/run-kit` → the whole-roster run silently skips it (graceful degradation working against us) and `shll update run-kit` errors `not installed`. The tool sits on 2.5.16 forever.
2. **Even unrenamed, today's roster can't cross the rename.** Delegating to `rk update` on a v2.x binary runs `brew upgrade sahil87/tap/rk`; whether the deleted-formula + rename-map resolution works depends on the old binary's version-check flow (`brew info --json=v2 sahil87/tap/rk`) — behavior shll cannot control, on binaries already shipped.
3. **PATH-probe surfaces mislead.** `shll list`/`version`/`doctor` probe `<Name> --version` (`version.go:72-88`). Renaming `Name` to `run-kit` breaks display for pre-2.5.13 installs (no `run-kit` alias binary); keeping `rk` shows a stale identity.
4. **Real-world pathologies already observed** on the author's machine during this session (see Observed States below) — the guard must classify them correctly, not just the happy path.

Why this approach (thin keg-gated guard + brew-native rename underneath) over uninstall→reinstall in the update path: no window where the tool is uninstalled; brew's `migrate` does the heavy lifting; one deterministic code path identical for linked and unlinked installs; and per-tool `update` delegation stays the norm for every non-migration run (Constitution IV — Composition).

## What Changes

### 1. Roster entry rename (`tools.go`)

```go
{Name: "run-kit", Formula: formulaPrefix + "run-kit", Update: []string{"run-kit", "update"}, Repo: "run-kit", Description: "Run-kit — tmux session manager with a web UI (rk stays as an alias)"},
```

- Roster position unchanged (leaves-first: the `rk -> wt` runtime edge becomes `run-kit -> wt`; update the ordering comment and `TestRosterLeavesBeforeDependents` references).
- `Repo` stays `run-kit` — the `Repo != Name` footgun note in `tools.go` inverts (now they match; the note about `github.com/sahil87/rk` being a 404 can be retired or repointed).
- Display name becomes `run-kit` immediately across `list`/`version`/`doctor` rows, the update digest, and JSON output. No transitional dual display.

### 2. Legacy target alias: `rk` → `run-kit` (`tools.go` `resolveTargets`)

- `shll update rk` and `shll install rk` must keep working (muscle memory, scripts). Add a legacy-alias lookup consulted during target resolution — e.g. a `map[string]string{"rk": "run-kit"}` checked before `rosterHas`, or an `Aliases []string` field on `Tool`; plan decides the shape.
- Resolution is to the canonical tool; the caller prints a one-line notice (e.g. `note: rk is now run-kit`). `resolveTargets` itself stays IO-free — return enough info for the caller to print.
- The valid-targets list in error messages shows canonical names only.
- `shll changelog rk@...`: in scope only if changelog's positional name-matching reuses the same helper (`changelog.go` matches names against `Roster` inline around line 237); otherwise a non-goal.

### 3. PATH-probe fallback (`version.go`)

- `probeToolVersion` (`version.go:72`) runs `<Name> --version`. Add a legacy-name fallback: when the primary name fails with `proc.ErrNotFound` **only** (not non-zero exit, not timeout — a present-but-broken `run-kit` must not silently defer to `rk`), retry with the legacy binary name `rk`.
- This flows through `toolInstalled` and `toolVersion`, i.e. `shll list`, `shll version`, `shll doctor` all see pre-2.5.13 installs (only `rk` on PATH) as installed.
- Display name in all these surfaces remains `run-kit` regardless of which probe name succeeded.
- Scope separation: this PATH fallback serves **display surfaces only**. The update/install migration gate is brew-keg-based (below) — a non-brew `rk` install is shown by list/version but never migrated by shll (parity with today's brew-only update behavior).

### 4. Migration guard in the update path (`update.go`, `brew.go`)

**Gate** (in `probeTool`, `update.go:445`): when `probeInstalledVersion(ctx, "sahil87/tap/run-kit")` reports not-installed OR reports an installed keg, classify by the **leaf name** parsed from `brew list --formula --versions` stdout (first field, e.g. `rk 2.5.13` vs `run-kit 3.0.0`):

1. Leaf `run-kit` → migrated; normal delegation path (`run-kit update [--skip-brew-update]`).
2. New-name probe not-installed → probe the legacy formula `sahil87/tap/rk`; stdout leaf `rk` → legacy keg → mark `probeResult` with `needsMigration: true`, `beforeVersion` from the legacy keg. (Observed state B shows the old-name probe can also report leaf `run-kit` post-migration — that is NOT legacy.)
3. Neither → not installed (unchanged).

`probeInstalledVersion`/`parseBrewVersion` (`brew.go:150`) currently discard the leaf token — extend to expose it (or add a sibling parser).

**Migration action** (replaces delegation for a `needsMigration` tool, in the sequential upgrade loop):

1. `brew upgrade sahil87/tap/rk` — brew resolves the rename and migrates the keg to `run-kit` 3.0.0. Always brew-direct: never delegate migration to the old binary (its rename handling is version-dependent and unfixable), never uninstall→install (failure window; that is the repair path via `shll uninstall`).
2. Post-check: if `run-kit --version` still fails with `ErrNotFound` (unlinked-keg pathology, observed state A), run `brew link run-kit`.
3. Print a note that the run-kit daemon, if running, was not restarted (brew-direct migration skips `rk update`'s post-upgrade restart side effect): suggest `run-kit serve --restart`. Print only — never run it (that would reimplement run-kit's own logic; Constitution III).
4. If the dual-rack leftover is detected (state C), print a one-line cleanup note; do not act on it.

**Plumbing requirements:**

- Both `shll update` (whole roster) and `shll update run-kit` flow through `probeTool` + the upgrade loop, so the guard applies to both — explicitly required by the user. The named-subset "not installed" error (`update.go:183-197`) must treat a legacy-keg machine as installed (the probe fallback achieves this).
- `shll update rk` resolves via the alias (change area 2) and behaves identically.
- **Dry-run** (`update.go:225-238`): the preview must show the real migration argv (`brew upgrade sahil87/tap/rk`) for a `needsMigration` tool — extend `upgradeArgv` or add a parallel single-source-of-truth so preview and live run cannot drift.
- **Digest**: `beforeVersion` comes from the legacy keg (e.g. `2.5.13`); the post-upgrade re-query must read the NEW formula (`installedVersion(ctx, "sahil87/tap/run-kit")`) so the digest renders `run-kit 2.5.13 → 3.0.0`. Release notes already key off `Repo: "run-kit"` — unchanged.
- Exit-code aggregation, sequential upgrade ordering, and per-tool output headers are unchanged; migration output renders under the tool's normal header.
- The guard is transitional: once legacy kegs die out, the fallback probe is a cheap no-op (`brew list` non-zero exit). Sunset in a future release; note this in code comments.

### 5. Install-path guard (`install.go`)

`shll install run-kit` (or whole-roster `shll install`) on a legacy-keg machine must not run `brew install sahil87/tap/run-kit` blind (brew may or may not auto-migrate on install; the observed dual-rack state C suggests exactly this kind of sequence created it). Reuse the same gate: legacy keg detected → run the migration action (area 4) instead of `brew install`. Migrated/absent → unchanged install behavior.

### 6. Doctor check (`doctor.go`)

- The PATH-probe fallback (area 3) flows through automatically.
- Add a WARN when the legacy `rk` keg (leaf `rk`) is still present — "pending migration — run `shll update run-kit`" — and when the dual-rack orphan (state C) is detected. Reuses the guard's detection helper; read-only.
- Verify the formula-trust list in `brew.go` references the new formula name.

### Non-Goals

- **No changes to run-kit itself** — the repo and tap are done (prerequisite, verified live).
- **No uninstall→install in the update path** — that sequence is the repair path, owned by the sibling `shll uninstall` change.
- **No generic unlinked-keg doctor check** for arbitrary tools — only the run-kit migration states.
- **No automatic cleanup of the dual-rack orphan** — detection + note only; cleanup via `shll uninstall` or manual brew.
- **No dynamic tool discovery** — the roster stays hardcoded (Constitution: Tool Roster Source of Truth).

## Open Questions

- On a genuine pre-migration machine (legacy `rk` keg + updated tap), what exactly do `brew list --formula --versions sahil87/tap/run-kit` and `... sahil87/tap/rk` report? The author's machine migrated mid-session, so this state can no longer be observed here. The dual-probe + leaf-parse design is robust to either outcome, but apply-stage tests should pin both parses; validating on a real legacy machine (or a scripted fixture) before release would confirm.
- Does v3 `run-kit update` restart the daemon when already up to date? Affects only the wording of the post-migration daemon note (a run-kit question, outside this repo).
