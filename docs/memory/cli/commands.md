# cli/commands

Top-level command surface for the `shll` binary — the cobra root, the subcommands it wires up, the exit-code translation layer, and the hardcoded tool roster every subcommand consumes.

## Binary entry point

`shll` is a single Go binary. The entry point is `src/cmd/shll/main.go:20`:

- The package-level `version = "dev"` (`src/cmd/shll/main.go:18`) is overridden via `-ldflags "-X main.version=<v>"` at build time. The literal default is `dev` (covers `go run` and unstamped local builds).
- `main()` builds the cobra root via `newRootCmd()`, sets `rootCmd.Version = version`, executes, and translates any `RunE` error to an exit code via `translateExit`.

## Cobra root

`newRootCmd()` (`src/cmd/shll/root.go:19`) returns the cobra command with:

- `Use: "shll"`
- `Short: "meta-CLI for the shll toolkit"`
- A `Long` block (`rootLong`, `src/cmd/shll/root.go`) listing the twelve user-facing subcommands and noting that per-tool CLIs continue to work standalone.
- `SilenceUsage: true` and `SilenceErrors: true` — usage is not printed on RunE errors, and cobra's default error printer is suppressed. The `translateExit` layer in `main.go` owns stderr.
- `AddCommand` (`src/cmd/shll/root.go`) wires **15 factory funcs**: `newDoctorCmd()`, `newInstallCmd()`, `newUpdateCmd()`, `newCheckUpdatesCmd()`, `newUninstallCmd()`, `newChangelogCmd()`, `newShellInitCmd()`, `newSetupCmd()`, `newVersionCmd()`, `newListCmd()`, `newStandardsCmd()`, `newSkillCmd()`, plus the three hidden factories `newShellSetupCmd()`, `newAgentSetupCmd()` (the hidden deprecated compat spellings — see [cli/setup](/cli/setup.md)), and the hidden `newHelpDumpCmd()`. The hidden commands are not counted in the user-facing surface (see [cli/help-dump-contract](/cli/help-dump-contract.md)), so the **user-facing surface is twelve**.

Per Constitution VII (Minimal Surface Area), every top-level subcommand requires explicit justification in the change's intake. The current user-facing surface is twelve subcommands (the hidden `help-dump` and the hidden compat spellings `shell-setup`/`agent-setup` are not counted — see [cli/help-dump-contract](/cli/help-dump-contract.md)).

### Constitution VII justification per subcommand

Every user-facing subcommand carries its own Constitution VII justification, reproduced here (each command's own memory file carries the fuller version — [cli/install](/cli/install.md#constitution-vii-justification), [cli/doctor](/cli/doctor.md), [cli/changelog](/cli/changelog.md#constitution-vii-justification), [cli/check-updates](/cli/check-updates.md#constitution-vii-justification), [cli/standards](/cli/standards.md#constitution-vii-justification), [cli/skill](/cli/skill.md#constitution-vii-justification), [cli/setup](/cli/setup.md#constitution-vii-justification), [cli/list](/cli/list.md#constitution-vii-justification)):

- **`skill`** (agst) — solves the agent-usage-knowledge gap: an agent driving a toolkit tool has no offline, version-locked "when to reach for which" briefing (`-h`/help-dump is flag reference; README/docs-site needs a checkout or network). `skill` composes each installed tool's own `<tool> skill` bundle at runtime — bare = a one-line-per-installed-tool glossary, `shll skill <tool>` = that tool's full bundle passed through byte-identical (`shll skill shll` = shll's own embedded bundle). Cannot be a flag on an existing subcommand: none reads or composes per-tool agent bundles, and the self-target embed needs special-casing (a subprocess self-invocation would recurse into the composer). Not a per-tool concern (Constitution IV) — cross-tool bundle aggregation is exactly the meta-tool's job. It is verbatim the `shell-init` composition pattern Constitution III/IV exist to bless. See [cli/skill](/cli/skill.md).
- **`setup`** (7p6b; halves from agst) — solves the setup-entry-point discoverability gap: the two machine-wiring halves were hard-to-rediscover hyphenated commands, so one `shll setup` family carries both — net **−1** visible top-level command (the old spellings survive hidden and uncounted). The halves' underlying justifications hold per half: the shell half solves the manual-rc-edit cliff in the post-`brew install` onboarding flow (cannot be a flag on `shell-init` — it *invokes* `shell-init`, so a sub-flag is structurally self-referential; cannot live in a per-tool CLI — it writes the cross-tool composition `eval "$(shll shell-init <shell>)"`, exactly what shll exists for; pure rc-wiring, per-formula Homebrew trust lives in `shll install` — 0854), and the agent half solves the harness-wiring-is-mis-homed gap (cross-toolkit harness wiring belongs in the manager, not a leaf tool; a distinct machine-provisioning verb, so not a flag on any existing subcommand). `shll install` auto-runs both halves at the end of install unless `--no-shell-setup`/`--no-agent-setup` (the [post-install auto-run steps](/cli/install.md#the-post-install-auto-run-steps-and-the-next-steps-block)). See [cli/setup](/cli/setup.md).
- **`standards`** (vo8c) — solves the standards-reachability gap: the toolkit gained binding, producer-facing standards (the ten CLI principles, the help-dump contract, the README/docs-site structure standard), but no way for an AI agent working in *any* toolkit repo to read them offline and without prior knowledge of where they live. Serving toolkit-wide standards is a cross-toolkit concern — exactly the meta-tool's job. Cannot be a flag on an existing subcommand — no existing subcommand reads or prints documents (`list` is the tool roster, `help-dump` is the machine help contract, `version` is a frozen bug-report table). Cannot live in a per-tool CLI — the standards govern all seven tools, so no single tool owns them (Constitution IV). The bare list form is a self-describing glossary (an agent told only "run `shll standards`" can pick the right document); `shll standards <name>` prints the canonical `docs/site/<name>.md` byte-identical, embedded at build time (offline, versioned with the release). See [cli/standards](/cli/standards.md).
- **`uninstall`** (kkaj) — solves the no-clean-slate-path gap: when brew state gets wedged (an unlinked keg, a half-failed upgrade), the only recovery was hand-typed brew surgery across up to seven formulas — `shll install` bootstraps but nothing removes. `uninstall` is a distinct **destructive** verb, not a variant of an existing operation: hiding it behind a flag on `install` (e.g. `--clean`) would bury a destructive action inside an additive command, and a per-tool CLI cannot own it (removing *all* toolkit members is inherently the meta-tool's job). See [cli/uninstall](/cli/uninstall.md).
- **`changelog`** (r01z) — solves the update-opacity gap: `shll update` upgrades up to eight tools but the record of *what changed* is buried in streamed output. Cannot be a flag on `update` — its core purpose is *deterministic re-display after the fact* (re-read notes without re-running an upgrade) and it has standalone value independent of updating (pre-update preview, historical range queries). Not a per-tool concern — its job is cross-toolkit release-notes aggregation, exactly shll's mandate. `shll update` *composes* it (printing a compact digest + the re-runnable `shll changelog ...` command), but the primitive is the standalone command. See [cli/changelog](/cli/changelog.md).
- **`doctor`** (d0ct) — solves the post-install verification gap referenced by the shll.ai docs (the install + idea pages name `shll doctor` as *the* verification step). Cannot be a flag on `version` — verification is a different concern (wiring checks, OK/WARN/FAIL semantics, a CI-meaningful non-zero exit) from version *reporting* (a plain table that always exits 0). Cannot be a flag on `install`/`update` — those *mutate*, whereas a doctor must be strictly read-only. Cannot live in a per-tool CLI — its value is the cross-tool aggregation plus the shll-owned rc-block wiring check (no single tool can see whether the *composed* shll block is present). Its `--json` is a flag on `doctor`, not a second subcommand. See [cli/doctor](/cli/doctor.md) for the full behavior contract.
- **`install`** — solves the bootstrap pain (a new user wants "get me the toolkit"). Distinct lifecycle from `update`: different precondition (not-installed vs. installed), different failure modes, different discoverability. Cannot cleanly fold into `update --install-missing` without inverting that command's installed-only precondition. See [cli/install](/cli/install.md) for the full justification and behavior.
- **`update`** — solves the no-single-update-command pain (`brew upgrade sahil87/tap/all` does NOT propagate to deps). Cannot be a flag on an existing tool because the entry point itself is what's missing. Also self-upgrades shll itself when shll was brew-installed — see [cli/update](/cli/update.md#shll-self-upgrade).
- **`check-updates`** (puxw) — solves the update-check-policy-is-mis-homed gap: a machine primitive for an external consumer (run-kit's daemon, which runs `shll check-updates --json --released`) plus an internal consumer (`shll changelog`), making shll the single policy authority so consumers never compile in `versions.json` parsing, version comparison, or notify-threshold policy. Cannot be a flag on `update` — `update`'s contract is to *perform writes* (even `--dry-run` previews brew commands rather than resolving latest versions), whereas `check-updates` resolves latest versions and writes nothing. Not a per-tool concern — whole-roster version resolution against the toolkit manifest is inherently the meta-tool's job (Constitution IV). `changelog` is the nearest neighbor but answers a different question (release *notes* vs. "is anything outdated, and does it cross the notify threshold?" as data). See [cli/check-updates](/cli/check-updates.md).
- **`shell-init`** — solves the cold-start cost and N-eval-line burden when multiple shell-integrating tools are installed. Per-tool `shell-init` keeps working standalone (Constitution IV).
- **`version`** — solves the bug-report triage pain. Cannot live on a per-tool CLI because the value is the cross-tool aggregation.
- **`list`** (lst7) — solves the toolkit-discovery gap (the shll.ai homepage advertises `shll list`). Cannot fold into `version`: `version` is deliberately frozen as plain-text-only, no-JSON, versions-only output for bug reports (version Design Decision #4), whereas `list` aggregates roster *metadata* (one-line descriptions + repo links) and needs structured `--json` — bolting that on would either break version's contract or be `list` in disguise. Not a per-tool concern (Constitution IV) — the value is the cross-tool aggregation. The roster it iterates is single-sourced with what `install`/`update`/`version`/`shell-init` consume, so it cannot drift from what's actually managed. See [cli/list](/cli/list.md#constitution-vii-justification) for the full justification and behavior.

## Exit-code translation

`translateExit(err error) int` in `src/cmd/shll/main.go` is the single mapping from `RunE` (and cobra-internal) errors to OS exit codes. It implements the **toolkit convention** — `0` success / `1` operational failure / `2` usage error (bad invocation) — stated by the principles standard, and shll's conformance to it is the audited receipt for principle №4 (see [cli/standards-conformance §usage errors exit 2](/cli/standards-conformance.md#1-usage-errors-exit-2-principle-4)). It uses two error sentinels defined in `src/cmd/shll/main.go`:

- `errSilent = errors.New("shll: silent error")` — returned by subcommands that have already written their own diagnostic to stderr. Maps to exit code 1; `translateExit` does not write anything else.
- `errExitCode{code, msg}` — used when a subcommand (or the root flag-error hook) needs an exit code other than the default. `shll shell-init` and `shll setup shell` construct it directly (still `errExitCode{code: 2, msg: …}` literals — NOT the `usageExitCode` constant) for their bad/missing-shell and related user-invocation errors (missing rc file, mutually-exclusive flags, corrupted block); the root `SetFlagErrorFunc` constructs it with `usageExitCode`. If `msg` is non-empty, `translateExit` writes it to stderr. It is matched via `errors.As`, so a wrapped `errExitCode` still yields its code (`TestTranslateExit_WrappedErrExitCode`).

### The `0/1/2` classification

`translateExit` classifies in this order — the first match wins (3sss):

1. **`errExitCode{...}`** (via `errors.As`) → its explicit `code`. This is how the exit-2 *usage* cases that flow through a typed path arrive: the root `SetFlagErrorFunc` (below) wraps flag-parse errors as `errExitCode{code: usageExitCode}`, and `shell-init`/`setup shell` wrap their own usage errors as code 2.
2. **`errSilent`** (via `errors.Is`) → `1` (operational failure; the caller already wrote its diagnostic).
3. **A cobra *arg/command* usage error** → `usageExitCode` (2). Cobra v1.10.2 exposes a clean hook only for *flag* errors; the arg/command usage errors it raises outside flag parsing (unknown command, invalid argument, wrong arg count) are plain `fmt.Errorf` values with **no typed sentinel**, so they are classified by their **stable message prefixes** via `isUsageError(err) bool` against the `cobraUsageErrorPrefixes` slice (`"unknown command "`, `"unknown flag: "`, `"unknown shorthand flag: "`, `"invalid argument "`, `"accepts "`, `"requires "`). Classification is **prefix-anchored** (`strings.HasPrefix`), not a loose substring search, so an operational error whose message merely *contains* a usage word mid-string stays exit 1. The root silences cobra's own usage/error printing, so `translateExit` writes the diagnostic to stderr itself here.
4. **Anything else** → `1` (operational failure); printed to stderr.

`usageExitCode = 2` is a **named constant** in `main.go` (code-quality.md: no magic numbers), single-sourced between `translateExit` and `root.go`'s `SetFlagErrorFunc`. The flag-error prefixes are absent from `cobraUsageErrorPrefixes` on purpose — flag errors are already wrapped into `errExitCode{code: 2}` by the hook before `Execute` returns — but including flag-error prefixes there would be harmless defense-in-depth (the code comment notes this).

### The root `SetFlagErrorFunc`

`newRootCmd()` (`root.go`) installs `cmd.SetFlagErrorFunc(func(_ *cobra.Command, err error) error { return &errExitCode{code: usageExitCode, msg: err.Error()} })` (3sss). Set on the **root** so every subcommand inherits it (cobra walks up to the root when a command sets no `FlagErrorFunc` of its own). This is the clean typed hook for flag-parse errors (unknown flag, bad flag value); the arg/command usage errors that carry no such hook are the ones `translateExit` classifies by prefix (above). Pinned by `TestRootCmd_FlagErrorIsUsageExit` (drives `root.Execute()` with a bad flag and asserts the error is an `errExitCode{code: usageExitCode}`).

The exit-code contract as a whole is pinned by `src/cmd/shll/main_test.go` (`TestTranslateExit_Contract` — the sentinel paths, the six cobra usage-error prefixes → 2, the mid-message operational error → 1; `TestTranslateExit_WrappedErrExitCode`; `TestRootCmd_FlagErrorIsUsageExit`).

Default fallback: any other error is printed to stderr and exits 1.

This layered design keeps cobra's own error printing out of the way (`SilenceErrors: true`) and concentrates exit-code policy in one place. The hop binary uses the same pattern; shll mirrors it.

## Subcommand factory pattern

Every subcommand follows `newXxxCmd()` returning `*cobra.Command` (no globals, no init() side effects). The cobra command's `RunE` calls a thin top-level helper (`runDoctor`, `runUpdate`, `runChangelog`, `runShellInit`, `runSetup`, `runShellSetup`, `runAgentSetup`, `runVersion`, `runList`) that takes explicit `io.Writer` arguments — this is the test seam: tests drive these directly with `bytes.Buffer` writers and a fake `proc.Runner` (or, for the shell half of `setup`, no fake — the command does file I/O only). `runChangelog(ctx, stdout, stderr, args)` additionally drives the [internal/changelog](/internal/changelog.md) `SetTransportForTest` seam to point release fetches at an `httptest.Server`. `runList(ctx, stdout, jsonOut bool)` adds a `bool` flag arg alongside the writer (the `--json` selector). `runDoctor` additionally takes an `env func(string) string` seam (production passes `os.Getenv`) so the wiring check reads a `t.TempDir()` rc file via a map-backed env — mirroring `resolveShell`/`resolveRcFile`.

## Hardcoded tool roster

Defined in `src/cmd/shll/tools.go`. Constitution III (Tool Roster Source of Truth) requires this to be hardcoded and versioned with the binary — there is NO runtime discovery (no `brew tap` parsing, no filesystem walk).

The `Tool` struct carries twelve fields: `Name`, `Formula`, `ShellInit`, `Update`, `Skill` (ktk5 — the skill-argv override, see below), `Description`, `Repo` (lst7), `SkillHint` (agst), `ProactiveHint` (pv7t — see below), `LegacyName` — the retained binary-alias/display field (see [The rk→run-kit rename](#the-rkrun-kit-rename)) — and the delegated (non-brew) seam pair `Install`/`Probe` (t26g — see below). Each `Roster` entry populates all the fields its capabilities require:

Roster invariants:

- **Order matters — importance-descending with dependency adjacency (t26g).** The slice is declared `run-kit, rk-desktop, fab-kit, wt, idea, tu, hop`: the tools a user reaches for first lead, and a delegated tool sits immediately after the runtime it depends on — rk-desktop directly after run-kit, whose `rk desktop …` subcommands it delegates to (run-kit's failure in a whole-roster `shll install` cascades to a skip-with-note for rk-desktop). `shll shell-init` concatenates output in roster order, `shll update`/`shll install` probe/upgrade/install in roster order, `shll uninstall` walks it in reverse, and `shll version`/`shll list`/`shll doctor` print rows in roster order — so the single declared order drives every consumer and no surface hardcodes a second order. The order is *output coherence and meaning*, not a correctness fix: brew already resolves formula dependencies correctly and idempotently regardless of walk order. The exact order is enforced by `TestRosterOrder` (`src/cmd/shll/tools_test.go`) — a comment cannot fail CI, so the test guards against an accidental reorder. See the [roster-order Design Decision](#design-decision-importance-descending-roster-order) below.
- **Seven tools.** Adding a tool is a `shll` release, not a runtime configuration change.
- **`Tool.ShellInit`** is the argv of the tool's shell-init invocation. Empty slice = no shell integration. The literal token `<shell>` (declared as `shellPlaceholder` in `src/cmd/shll/tools.go:167`) is substituted with the user-supplied shell name (`zsh`/`bash`) at composition time. All three integrators (`tu`, `hop`, `wt`) substitute the placeholder uniformly — three of the seven roster entries carry shell integration.
- **`Tool.Update`** (cczs) is the argv of the tool's own `update` invocation, mirroring `ShellInit`'s "empty slice means no capability" semantics. `shll update` delegates to this argv (appending `--skip-brew-update` when the tool advertises it) instead of calling `brew upgrade <formula>` directly, so each tool's post-upgrade side effects (e.g. run-kit's daemon restart) are preserved (Constitution IV). For a delegated (non-brew) tool this IS the update path — rk-desktop's is `{"rk", "desktop", "update"}` (t26g) — with no brew fallback (there is no formula). An empty slice on a brew-managed tool means the tool exposes no `update` subcommand → `shll update` falls back to `brew upgrade <formula>`. **All seven current roster entries populate `Update`** — every shll tool ships an `update` subcommand. See [cli/update](/cli/update.md#behavior-contract) for the delegation/probe logic.
- **`Tool.Skill`** (ktk5) is the argv of the tool's skill-bundle invocation, mirroring `ShellInit`'s "empty slice means no divergence" semantics. `shll skill <tool>` / `shll skill <tool> <topic>` resolve it via the `skillArgv(tool)` helper (`skill.go`) — the override when populated, else the default `{Name, "skill"}` — so neither passthrough open-codes the argv. **Exactly one entry populates it — fab-kit → `{"fab", "skill"}`** — because fab-kit serves its skill bundle on the `fab` router binary, not the `fab-kit` binary; every other tool derives the default. Skill-only: `update`/`install`/`version`/`list`/`doctor` key off `Name`/`Formula`/`Update` and are untouched, and the bare-glossary install probe still keys on `Name`. See [cli/skill §the skill-argv override](/cli/skill.md#the-skill-argv-override-fab-kit--fab-skill).
- **`Tool.Description`** (lst7) is a one-line, human-readable summary printed by `shll list` and the bare `shll skill` glossary. Single-sourced on the roster so it cannot drift from the managed set (Constitution III). All seven entries populate it (guarded by `TestList_RosterFieldsNonEmpty`). run-kit's is `"Run-kit — tmux session manager with a web UI; can display web pages/HTML to the user, push notifications, and run VS Code palette commands in its code editor via `rk code exec` (rk stays as an alias)"` — it carries display/notify/editor-command vocabulary so every hop-1 surface renders the capabilities (pv7t, e0gt).
- **`Tool.SkillHint`** (agst) is a short reactive task-domain phrase (`"git worktrees"`, `"backlog ideas"`, run-kit's `"tmux sessions"`) woven into the generated `shll setup agent` skill description as a `hint (name)` clause so agents match on task vocabulary, not just tool names. Required for every roster entry (guarded by `TestRosterSkillHints`). See [cli/setup §the description builder](/cli/setup.md#the-description-builder-agentskilldescription).
- **`Tool.ProactiveHint`** (pv7t) is complete sentence(s)/prose describing *agent-proactive* capabilities — ones the agent should reach for **unprompted** (without the user naming a tool) — appended verbatim to the generated `shll setup agent` description after the tool clauses. **Optional-by-design and empty for every tool except run-kit** (the sprawl guard: only agent-proactive capabilities earn description space; reactive tools stay behind the two-step router because the user's words name them). run-kit's is a two-sentence value: sentence one names its agent-proactive capabilities — visual display, proxying a local http port to the user's browser, notify, and acting inside the user's code editor with `rk code exec` (e0gt); sentence two is a skill-shadowing counter-instruction sending the agent to `shll skill run-kit` before it opens any file or local port in a browser or publishes a hosted artifact (xv71, e09x). Single-sourced on the roster (Constitution III) so the description cannot drift; guarded by `TestRosterProactiveHint`, which also pins the four load-bearing fragments. See [cli/setup §the description builder](/cli/setup.md#the-description-builder-agentskilldescription) and [§the ProactiveHint does four jobs](/cli/setup.md#design-decision-the-proactivehint-does-four-jobs).
- **`Tool.Repo`** (lst7) is the `github.com/sahil87/<Repo>` slug for the tool's source repository, used by `shll list` to render the repo column. `Name == Repo` holds for every brew-managed entry; rk-desktop's `Repo` is `run-kit` — it ships with the run-kit repo and has no repo of its own (t26g). The field stays explicit (not derived from `Name`) so `shll list` never emits a dead link when a tool's binary name and repo slug diverge — rk-desktop is the live case: deriving its slug from `Name` would emit the dead `.../rk-desktop` link. The single URL-composition point is `repoURL(t)` (`src/cmd/shll/list.go`) = `githubOrgBase + t.Repo`, guarded by `TestList_RepoLinks` (asserts run-kit resolves to `.../run-kit` and the dead `.../rk` link is absent). See [cli/list §The run-kit repo-slug footgun](/cli/list.md#the-run-kit-repo-slug-footgun).
- **`Tool.Install`** (t26g) is the argv of the tool's delegated install invocation — rk-desktop's `{"rk", "desktop", "install"}`. Empty for brew-managed tools, whose install path is `brew install <Formula>`. A non-empty `Install` marks the delegated (non-brew) seam: such a tool carries NO `Formula`, is skipped by every brew-centric helper (trust, `brew list`, `brew upgrade`, `brew uninstall`), and MUST carry a `Probe`. Populated only by rk-desktop; the seam is field-driven (no name-keyed special-casing outside the roster declaration), so a future non-brew tool needs only a roster entry.
- **`Tool.Probe` / `ToolProbe`** (t26g, `src/cmd/shll/tools.go:121`) is the installed-state probe spec for a delegated tool — the non-brew counterpart of the `brew list --versions` probe and the `<tool> --version` PATH probe; nil for brew-managed tools. `ToolProbe{Argv, LinePrefix, AbsentValue}`: run `Argv` via `proc.RunCaptured` (both streams captured, so a platform-refusal message on either stream is detectable), then scan the output for a line starting with `LinePrefix` — value == `AbsentValue` → not installed; any other value → installed and the value IS the version; no matching line, a transport error, or a non-zero exit → not installed. rk-desktop's probe is `{"rk", "desktop", "status"}` parsing the `Installed:` line (`Installed: not installed` → absent; `Installed: v<X>` → present with version `v<X>`). rk-desktop's run-kit dependency is expressed as this runtime probe + roster adjacency only (install-composition standard, Policy A — no formula edge, no `depends_on`).
- **`brewManaged()`** (t26g, `src/cmd/shll/tools.go:135`) reports whether the tool is installed/upgraded/removed through Homebrew (`Formula != ""`) — the delegated seam is its inverse, so every brew-centric helper (trust, `brew list`, `brew upgrade`, `brew uninstall`) MUST branch on it before touching a formula.
- **rk-desktop platform gating** (t26g) is probe-based, never a hardcoded `runtime.GOOS`/darwin check: `rkBinary = "rk"` (`src/cmd/shll/tools.go:141`) is the argv[0] every `rk desktop …` delegation runs through, and `rkDesktopRefusalToken = "rk desktop is macOS-only"` (`src/cmd/shll/tools.go:150`) + `isRkDesktopRefusal(out []byte)` match run-kit's `errDesktopMacOnly` message on either captured stream to distinguish a platform refusal (skip-with-note in whole-roster runs, an explicit message on a targeted run) from a real failure — so run-kit growing Linux support needs zero shll changes.
- **`formulaPrefix = "sahil87/tap/"`** (`src/cmd/shll/tools.go:11`) is a named constant — no magic string at the call sites.
- **`githubOrgBase = "https://github.com/sahil87/"`** (`src/cmd/shll/tools.go:162`, lst7) is the named constant for the GitHub org base URL — `shll list` never open-codes the URL prefix (code-quality.md). A tool's repo URL is `githubOrgBase + tool.Repo`.

## The rk→run-kit rename

run-kit's binary/formula name is `run-kit`; its prior name was `rk` (the tap installs the binary as `run-kit` with `rk` kept as an interchangeable command alias; `formula_renames.json` maps `{"rk": "run-kit"}`). The rename leaves shll two retained compatibility surfaces — a `Tool.LegacyName` display fallback and a target alias — and **no formula-migration machinery**: shll never probes or acts on the legacy `sahil87/tap/rk` formula (see [cli/update §Retire the migration guard](/cli/update.md#retire-the-rkrun-kit-brew-formula-migration-guard)). The roster facts:

- **run-kit's roster entry** — `Name: "run-kit"`, `Formula: "sahil87/tap/run-kit"`, `Update: {"run-kit", "update"}`, `Repo: "run-kit"` (`Name == Repo`), 1st position (it heads the roster). The display name is `run-kit` everywhere — `list`/`version`/`doctor` rows, the update digest, and JSON output.
- **`LegacyName string`** (`"rk"`, empty for every other tool) — the tool's PRIOR binary name, retained as a **binary-alias/display surface** (the run-kit formula still installs `rk` as an interchangeable command alias). Used ONLY as a display-surface PATH-probe fallback: when `<Name> --version` returns `proc.ErrNotFound`, `probeToolVersion` retries `<LegacyName> --version` so an install whose binary is on PATH under `rk` is shown installed by `list`/`version`/`doctor`. It is NOT tied to formula migration. See [cli/version §the legacy-name PATH-probe fallback](/cli/version.md#the-legacy-name-path-probe-fallback).

### The legacy target alias (`rk` → `run-kit`)

So `shll update rk` / `shll install rk` / `shll uninstall rk` (muscle memory, existing scripts) keep working, a package-level map `legacyAliases = map[string]string{"rk": "run-kit"}` (`src/cmd/shll/tools.go`) is consulted inside `resolveTargets` **before** `rosterHas` — an aliased arg resolves to its canonical Roster tool. The mechanism:

- **`resolveTargets(args, allowShll) (selected []Tool, selfSelected bool, aliased []string, err error)`**. It stays **IO-free** (no brew/subprocess calls); when an arg matches a `legacyAliases` key whose canonical name is in the roster, it records the alias token in `aliased` (in encounter order) so the *caller* can print the notice. `resolveTargets` never prints — IO is the caller's concern.
- **`printAliasNotices(stdout, aliased)`** (`tools.go`) writes one `note: rk is now run-kit` line per aliased token (format constant `aliasNoticeFmt = "note: %s is now %s"`), to **stdout** (a friendly note, not an error). Shared by `update`/`install`/`uninstall` so the wording is single-sourced; `changelog` gets the alias for free because `parseChangelogSpecs` routes names through the same `resolveTargets` (though changelog does not print the notice — it re-derives its own ordering).
- **Aliases are NEVER advertised in the valid-targets error diagnostic.** `validTargets(allowShll)` derives from the live `Roster` (+ `shll` when `allowShll`), so `shll update foo` errors `unknown target "foo" (valid targets: shll, run-kit, rk-desktop, fab-kit, wt, idea, tu, hop)` — no `rk`. Accepted-but-unadvertised is the deliberate contract.

The alias is a retained compatibility surface alongside `LegacyName`; both are the binary-alias/display concerns the rename left behind, distinct from the retired formula-migration guard.

## The shared `shllSelf` descriptor

`shll` is the manager-member of the toolkit, but it is **deliberately NOT in `Roster`** — `Roster` is the *managed sub-tool* list (Constitution III). To represent shll uniformly across the commands that show the toolkit, a **single shared descriptor** in `src/cmd/shll/tools.go` is the one source of truth for "shll as a displayable entry" (bb7r):

```go
const shllSelfDescription = "the manager for the shll toolkit"

var shllSelf = Tool{
    Name:        shllTargetToken, // "shll"
    Description:  shllSelfDescription,
    Repo:        shllTargetToken, // → https://github.com/sahil87/shll via repoURL
}

func shllSelfVersion() string { return normalizeVersion(version) } // package var, never `shll --version`
```

- **Reuses the `Tool` struct shape, but is not a `Roster` entry.** Only `Name`, `Description`, and `Repo` are populated. shll has no managed `Formula`, no own `ShellInit` to compose, and is self-upgraded via `update.go`'s dedicated path rather than a `Roster` `Update` argv. **Why not add shll to `Roster`** (the rejected alternative): it would violate Constitution III, break the roster-order invariant guarded by `TestRosterOrder`, and make `install`/`update`/`shell-init` try to operate on the running orchestrator itself (e.g. `brew install` the live binary). `len(Roster)` stays **7**; `TestShllSelf_NotInRoster` guards `len(Roster) == 7` and `!rosterHas("shll")`.
- **Version from the package var, never a self-subprocess.** `shllSelfVersion()` returns `normalizeVersion(version)` (the same package-level `version` var `shll version`'s first row reads), so shll's version display is consistent across surfaces and no `shll --version` self-spawn is ever issued (shll is always present — it is the running process). `TestShllSelfVersion_FromPackageVar` pins this; `TestShllSelf_Descriptor` pins the field contract (`Name`/`Description`/`Repo`, and that `Formula`/`ShellInit`/`Update` are empty).

### Unified shll-first ordering — the principle

Every command that meaningfully shows the toolkit renders **shll FIRST, then the `Roster`** (`shll, run-kit, rk-desktop, fab-kit, wt, idea, tu, hop`):

| Command | shll-first instance | bb7r code change? |
|---------|---------------------|-------------------|
| `version` | leads with a `shll` row (version from the package var) | **No** — already shll-first |
| `update` | leads with the `shll (self)` step as `[1/M]` | **No** — already shll-first |
| `list` | prepends a shll-first table row (plain installed marker) + a `--json` object carrying `self:true` (`omitempty`) | **Yes** ([why a self-row](/cli/list.md#why-a-self-row)) |
| `doctor` | prepends an always-OK shll-first row/object (checks 1+2 only, `shell_init:false`, never touches `anyFail`, excluded from the problem-count denominator) | **Yes** ([cli/doctor](/cli/doctor.md#the-prepended-shll-first-row)) |
| `install` | prepends a shll-first **informational** line (`"shll — already present / self-managed"`) — never a brew action | **Yes** ([cli/install](/cli/install.md#the-prepended-shll-first-informational-line)) |
| `shell-init` | **excluded** — the one documented exception | n/a |

`version` and `update` keep their own inline shll-first handling, agreeing with `shllSelf` by construction (same package version var); `list`/`doctor`/`install` consume `shllSelf` for the displayable Name/Description/Repo.

**`shell-init` is the one deliberate exception.** It is the only toolkit-showing command that does NOT prepend a shll entry: shll has no shell-init output of its own to compose, and `shell-init`'s stdout is `eval`'d, so a stray shll line risks breaking the user's shell (Constitution V eval-safety). See [cli/shell-init §the deliberate exception](/cli/shell-init.md#the-deliberate-exception--do-not-unify-onto-the--header).

**The self-row is a display decision, not a Constitution rule.** `list` carries a shll self-row **for discoverability** (a newcomer should see shll as part of the family). The decision is recorded in three live locations — `docs/memory/cli/list.md`, the `runList` doc comment in `list.go`, and `README.md` — and is **not** promoted to a constitutional rule (Constitution VII's new-subcommand bar is not triggered: it is behavior on existing commands, not a new subcommand). (bb7r)

### Design Decision: Importance-descending Roster order

**Decision**: The `Roster` is declared in **importance-descending order with dependency adjacency** — the exact order `run-kit, rk-desktop, fab-kit, wt, idea, tu, hop`, enforced by `TestRosterOrder` (`src/cmd/shll/tools_test.go`), an exact-order assertion (a comment cannot fail CI, so the test guards against an accidental reorder). The tools a user reaches for first lead; a delegated tool sits immediately after the runtime it depends on — rk-desktop directly after run-kit, whose `rk desktop …` subcommands it delegates to. Every roster-driven surface (install/update walk order, uninstall's reverse walk, list/doctor/version row order, shell-init composition order) inherits the order from the single slice — no surface hardcodes a second order.

**Why**: the order carries meaning. Importance-descending reflects the reach-for-first usage pattern; adjacency puts rk-desktop next to its runtime dependency run-kit, whose failure in a whole-roster `shll install` cascades to a skip-with-note for rk-desktop. Brew already owns formula-dependency resolution (correct and idempotent regardless of walk order), so the order is output coherence and meaning, never correctness.

**Rejected**: ordering by runtime/brew dependency edges (dependency edges are not the ordering principle — brew owns the formula graph and each `<tool> update` is self-update-only); a second, per-surface order (drift risk — two orderings to keep in sync); a `DependsOn` field with a runtime topological sort (models the inter-tool graph as shll-owned data — shll's contract is the hardcoded roster *list* per Constitution III, and the graph is brew's and the sub-tools' concern).

*Introduced by*: `260820-t26g-roster-desktop-entry`.

## Shared UI helper (`ui.go`)

Three commands frame their per-tool output via the shared `ui.go` helper (y630), so the TTY/`NO_COLOR`/glyph logic lives in exactly one place:

- [cli/update](/cli/update.md#per-tool-output-separation) — per-tool `▸ [N/M]`/`==> [N/M]` header (including `shll (self)`) + summary tail + the `--dry-run` preview.
- [cli/install](/cli/install.md#per-tool-output-separation) — mirrors update's header + tail + preview.
- [cli/shell-init](/cli/shell-init.md#shell-comment-separator) — `# ── <tool> ──` comment separator only; deliberately **not** the header/color path (eval-safety).

`golang.org/x/term` (TTY detection) is the codebase's only color/terminal dependency (y630) — its sole terminal inspection. `version` deliberately does not use the header path (its lines already self-label).

`update` and `install` route their write-phase children through `brew.go`'s `runStreamedChild` (null-stdin `proc.RunStreamedTail` with a live tee to the run's writers) — one linear stream with full scrollback. See [cli/update §null-stdin streamed children](/cli/update.md#null-stdin-streamed-children).

### Output polish + `--dry-run`

Four presentation features apply to **both** `update` and `install` via `ui.go` + the `clock.go` seam (6vuo):

1. **`[N/M]` progress counters** in the per-tool header — `printToolHeader` gained `pos, total int` parameters. For `update`, `M = installed-roster-count + (1 if shll is brew-installed)`, computed up front, with `shll (self)` as `[1/M]` and first; for `install`, `M = len(missing)`.
2. **Section spacing** — a blank line before each per-tool header except the first, and a blank line before the summary tail (emitted by the commands, not the helper). Empty/short-circuit cases emit none.
3. **Run duration in the summary tail** — `printSummaryTail` gained an `elapsed time.Duration` parameter, appending `in <dur>` to both the success and partial-failure forms (duration before the em-dash in the partial form). Measured via the `nowFunc` clock seam (`clock.go`). Duration is a run fact, not an outcome claim — the honesty constraint is preserved.
4. **`--dry-run` flag on `update` and `install`** — a cobra bool flag (`dryRunFlag`/`dryRunFlagUsage` named constants in `update.go`, shared by both commands; threaded as a `dryRun bool` parameter into `runUpdate`/`runInstall`). When set, the read-only probes still run but **no write** is performed; the command prints an aligned-column preview (`printUpdatePreview`/`printInstallPreview`) of the exact per-tool commands and exits 0. This is a **flag on existing commands, NOT a new subcommand** — Constitution VII's "could this be a flag?" test is satisfied, so it does not affect the surface-area count. See [cli/update §`--dry-run`](/cli/update.md#dry-run) and [cli/install §`--dry-run`](/cli/install.md#dry-run).

The `update` dry-run preview renders each tool's command from the **shared `upgradeArgv`** (`update.go`) — the single source of truth `upgradeTool` uses for the live run, so the preview can never drift from what the run would do — joined to a display string via `argvString`. `ui.go` stays presentation-only: it receives already-built `[]previewRow` and only aligns/prints them, keeping all subprocess knowledge in the command files (Constitution I).

### Bold-cyan header run + the `bold` anchor helper

Two presentation-only behaviors in `ui.go`, both TTY-gated via the existing threaded `color` decision (13k3):

1. **Whole-run bold-cyan header.** `printToolHeader`'s color branch renders the entire `▸ [N/M] <tool>` run inside a **single bold-cyan span** (`ansiBoldCyan` … `ansiReset`). Because all three surfaces share this function, it covers `shll update`, `shll install`, and `shll changelog` uniformly. The plain branch (`==> [N/M] <tool>`, non-TTY / `NO_COLOR`) carries no ANSI. Pinned by `TestPrintToolHeader_ColorForm` (bold-cyan run) / `TestPrintToolHeader_PlainForm`.
2. **`bold(color, s)` anchor helper.** A new helper wraps `s` in `ansiBold` … `ansiReset` when `color`, else returns `s` unchanged — the single place the changelog-surface anchor styling (the digest / `shll changelog` transition lines and the release tag/title lines) is applied, so no call site open-codes an escape (code-quality.md: named constants, no magic strings). It mirrors the `arrow`/`dash`/`more` glyph-helper idiom. Deliberately **plain bold, NOT bold-cyan** — bold-cyan stays reserved for `printToolHeader` so the visual hierarchy header > anchor > body is preserved. Consumed by `renderChangelogResult`/`renderReleases` (`changelog.go`) and `printUpdateDigest` (`update.go`). See [cli/update §digest rendering](/cli/update.md#digest-rendering-printupdatedigest) and [cli/changelog §output shape](/cli/changelog.md#output-shape).

## Cross-references

- Constitution I (Security First) → all subprocesses go through [`internal/proc`](/internal/proc.md); network I/O is likewise isolated in the internal packages [`internal/changelog`](/internal/changelog.md) and [`internal/versions`](/internal/versions.md) (the only `net/http` importers — no `cmd/shll` file imports it, guarded by `TestCmdShllNoNetHTTP`, r01z/puxw). (`ui.go` makes no subprocess calls — it is pure presentation.)
- Constitution III (Wrap, Don't Reinvent) + IV (Composition, Not Replacement) → every subcommand shells out; nothing reimplements brew or per-tool logic. shll's framing prints only *around* each subprocess; sub-tool bytes are never rewritten.
- Constitution V (Graceful Degradation) → uninstalled tools never produce errors; missing tools are skipped silently. Eval-safety drives `shell-init`'s comment-separator exception (see [cli/shell-init](/cli/shell-init.md#the-deliberate-exception--do-not-unify-onto-the--header)).
- Constitution VII (Minimal Surface Area) → the user-facing subcommand list is twelve (`doctor`, `install`, `update`, `check-updates`, `uninstall`, `changelog`, `shell-init`, `setup`, `version`, `list`, `standards`, `skill`). Each carries its own justification — see the [per-subcommand justification](#constitution-vii-justification-per-subcommand) above. Flags (`--dry-run`, `--json`), helper files (`ui.go`, `clock.go`), aliases, hidden compat spellings (`shell-setup` with the `shell-install` alias, `agent-setup`), and added behavior on existing commands do not raise the count.
- Constitution III (Tool Roster Source of Truth) → `shll` is deliberately NOT in `Roster` (the managed sub-tool list); the shll-first display entry is the prepended shared `shllSelf` descriptor, so `len(Roster)` stays 7 and the `TestRosterOrder` invariant is untouched — see [the shared `shllSelf` descriptor](#the-shared-shllself-descriptor).
